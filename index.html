1. 先理解 CPA 和 NewAPI 的关系

CPA 的作用：在本机启动一个 OpenAI 兼容 API 服务，把 Codex / OpenAI / Gemini / Claude 等认证统一管理起来。

NewAPI 的作用：把 CPA 当成一个普通 OpenAI 上游渠道，统一分发给你的客户端使用。

1
客户端发起请求

例如 ChatBox、Cherry Studio、Cursor、Open WebUI 或你自己的应用。

入口层
2
NewAPI 接收并转发

NewAPI 只需要访问本机或局域网里的 CPA 地址。

不需要额外挂梯子
3
CPA 负责真正访问上游

CPA 根据认证 JSON、API Key、代理配置去访问 OpenAI / Codex 等服务。

必须配置代理
4
代理连接海外服务

真正出国的是 CPA，因此代理写在 CPA 的 proxy-url。

核心是 proxy-url
最重要的结论：NewAPI 不需要额外挂梯子。只要 NewAPI 能访问 CPA 的 http://127.0.0.1:8317/v1，真正的代理问题交给 CPA 处理。

2. 下载正确的 Windows 安装包

1

打开官方 Release 页面

浏览器访问：

https://github.com/router-for-me/CLIProxyAPI/releases
2

普通 Windows 电脑下载 amd64 包

大多数 Intel / AMD 台式机或笔记本，下载这个：

CLIProxyAPI_7.1.44_windows_amd64.zip
文件名适用场景
windows_amd64.zip普通 Intel / AMD 64 位 Windows。绝大多数电脑选这个。
windows_aarch64.zipWindows ARM 设备，例如骁龙 ARM 笔记本。
linux_amd64.tar.gzLinux x64 服务器。
darwin_amd64 / darwin_aarch64macOS，对应 Intel Mac / Apple Silicon Mac。

3. 整理安装目录

建议统一安装到：

D:\CLIProxyAPI

解压后一般会看到这些文件：

  • cli-proxy-api.exe
  • config.example.yaml
  • README.md
  • README_CN.md
  • LICENSE

建议把这些文件都放到 D:\CLIProxyAPI，最终结构如下：

D:\CLIProxyAPI
├─ cli-proxy-api.exe
├─ config.example.yaml
├─ config.yaml
├─ README.md
├─ README_CN.md
└─ LICENSE
不建议保留成 D:\CLIProxyAPI\CLIProxyAPI_7.1.44_windows_amd64\... 这种套娃路径。路径越短，后续排查越简单。

4. 创建并修改 config.yaml

不要自己手写一个只有几行的 config.yaml。必须复制完整的 config.example.yaml，否则可能出现 API server started successfully on :0，导致 8317 访问不了。
1

复制完整配置模板

复制：

D:\CLIProxyAPI\config.example.yaml

重命名为：

D:\CLIProxyAPI\config.yaml
2

确认端口是 8317

打开 config.yaml，确认有：

host: ""

port: 8317

port: 8317 是 CPA 后台和 API 的监听端口。

3

设置管理后台密码

找到：

remote-management:
  allow-remote: false
  secret-key: ""

改成自己的密码，例如：

remote-management:
  allow-remote: false
  secret-key: "admin123"
第一次启动后，CPA 可能会把明文密码自动改成 $2a$... 这种哈希，这是正常现象。登录后台仍然用你设置的原始密码，例如 admin123。
4

设置给 NewAPI 用的 API Key

找到：

api-keys:
  - "your-api-key-1"
  - "your-api-key-2"
  - "your-api-key-3"

建议改成一个自己定义的 Key：

api-keys:
  - "sk-cpa-test-123"
配置项用途谁使用
remote-management.secret-key登录 CPA 管理后台人，在浏览器里登录
api-keys调用 CPA 的 OpenAI 兼容接口NewAPI / Cherry Studio / Cursor 等客户端

5. 给 CPA 配置代理

如果要使用 OpenAI / Codex / Claude / Gemini 等海外服务，CPA 必须能走代理。

在 config.yaml 中找到：

proxy-url: ""

如果你用 Clash / Mihomo，常见 HTTP 代理端口是 7890：

proxy-url: "http://127.0.0.1:7890"

如果你用 SOCKS5 代理，常见端口可能是 1080：

proxy-url: "socks5://127.0.0.1:1080"

如果代理需要用户名密码：

proxy-url: "http://用户名:密码@127.0.0.1:7890"
如果刷新配额时报 auth.openai.com/oauth/token EOF，优先检查这里。常见处理方式：确认代理端口、代理软件切全局模式、换一个支持 OpenAI 的节点。

6. 启动 CPA 并进入后台

1

启动程序

双击运行：

D:\CLIProxyAPI\cli-proxy-api.exe
2

看控制台日志

成功标志：

API server started successfully on :8317

管理后台注册成功：

management routes registered after secret key configuration
如果看到 API server started successfully on :0，说明 config.yaml 不完整，或者程序没读到完整配置。回到第 4 步重新复制完整配置模板。
3

打开管理后台

浏览器访问：

http://localhost:8317/management.html

使用 remote-management.secret-key 设置的密码登录。

7. 上传认证 JSON 并刷新配额

1

上传认证文件

进入 CPA 后台左侧菜单：

认证文件管理 / Auth Files

点击上传，把 Codex / OpenAI 的认证 JSON 上传进去。

2

确认认证文件被识别

页面上应该能看到类似：

  • 认证文件数量：1
  • 类型：Codex
  • 文件名：例如 01.json

CPA 控制台可能出现：

full client load complete - 1 clients (1 auth entries ...)
3

刷新配额

进入配额管理，点击刷新。

现象含义处理
能显示额度认证与代理基本成功继续接入 NewAPI
EOFOpenAI OAuth 连接被中断检查 proxy-url、切全局、换节点
401 / 403认证失效或权限问题重新上传 JSON 或重新登录
超时网络或代理不稳定换节点，确认代理端口

8. 把 CPA 接入 NewAPI

NewAPI 里把 CPA 当成一个普通 OpenAI 渠道即可。

NewAPI 配置项填写内容
渠道类型OpenAI
渠道名称CPA-Codex 或 CPA-本地
Base URLhttp://127.0.0.1:8317/v1
API Key填写 CPA 的 api-keys，例如 sk-cpa-test-123
如果 NewAPI 和 CPA 在同一台电脑上，用 http://127.0.0.1:8317/v1。
如果 NewAPI 跑在 Docker 里，127.0.0.1 指的是容器自己，不是宿主机。此时要用宿主机 IP、Docker 网关地址，或 host 网络模式。

9. 常见错误排查

问题最可能原因解决方法
浏览器打不开 localhost:8317CPA 没启动，或端口不是 8317看控制台是否有 :8317。如果是 :0，修复 config.yaml。
日志显示 started successfully on :0config.yaml 不完整用完整 config.example.yaml 复制为 config.yaml。
登录后台失败管理密码不对检查 remote-management.secret-key。如果已变成 $2a$...，仍用原始密码登录。
刷新配额报 EOF代理没通、规则没覆盖、节点被拒绝配置 proxy-url，代理切全局，换支持 OpenAI 的节点。
GitHub rate limit exceededGitHub API 限流通常不影响 CPA 主功能。只要后台能打开，可暂时忽略。
NewAPI 渠道测试失败Base URL / API Key 错，或 CPA 不可达确认 http://127.0.0.1:8317/v1 和 api-keys。
Cherry Studio 能用，但 Codex 401协议、模型名、认证状态或 API Key 不一致先请求 /v1/models 看模型列表，再检查 CPA 日志是否有 401 或 EOF。

10. 最终验收流程

1
下载

在 GitHub Release 下载 CLIProxyAPI_xxx_windows_amd64.zip。

2
放置

解压后把 cli-proxy-api.exe 和 config.example.yaml 放到 D:\CLIProxyAPI。

3
配置

复制 config.example.yaml 为 config.yaml，确认 port: 8317，设置后台密码、api-keys 和 proxy-url。

4
启动

运行 cli-proxy-api.exe，日志必须看到 API server started successfully on :8317。

5
认证

打开 http://localhost:8317/management.html，上传 Codex / OpenAI JSON，并刷新配额。

6
接入

NewAPI 添加 OpenAI 渠道，Base URL 填 http://127.0.0.1:8317/v1，API Key 填 CPA 的 api-keys。

一句话记住：CPA 是真正访问 OpenAI / Codex 的本地中转层；NewAPI 只需要把 CPA 当成 OpenAI 上游，填 http://127.0.0.1:8317/v1 和 CPA 的 api-keys 即可。
